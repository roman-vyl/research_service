## MODIFIED Requirements

### Requirement: Request contract

`POST /api/research/backtests` SHALL accept a Research backtest envelope
containing exactly one canonical strategy-instance **identity subset**
(`strategy_id`/`ticker`/`base_timeframe`/`raw_spec`, as defined by
`canonical-strategy-instance-v1`) plus backtest-specific concerns: range
specification, execution policy, accounting policy, and the
managed-policy toggle. The envelope SHALL NOT accept `family`, `variant`,
`strategy_version`, `enabled`, or a caller-supplied `instance_id` as
request fields — backtest evaluation depends only on the identity subset,
never on deployment metadata.

#### Scenario: Valid request accepted

- **WHEN** a well-formed request envelope wrapping one canonical
  strategy-instance identity subset is posted
- **THEN** the endpoint accepts it and begins orchestration.

#### Scenario: Legacy identity field rejected

- **WHEN** a request includes `family`, `variant`, `strategy_version`, or
  an explicit `instance_id`
- **THEN** the request is rejected before orchestration begins.

## REMOVED Requirements

### Requirement: Duplicate run rejection

**Reason**: `run_id` is no longer a caller-supplied field (see the new
"Server-generated run identity" requirement), so a caller can no longer
trigger a duplicate-run-id submission. Collision is now an
implementation-internal concern of `run_id` generation, not a
client-facing error path.

**Migration**: Callers that previously chose a `run_id` and handled
`409 run_already_exists` on resubmission SHALL stop sending `run_id` and
SHALL instead treat the run identity Research Service returns in the
success response as authoritative.

## ADDED Requirements

### Requirement: Server-generated run identity

`run_id` SHALL be generated by Research Service and SHALL NOT be a
request field. The generated `run_id` SHALL be returned to the caller in
the success response and SHALL be used as the artifact persistence key.

#### Scenario: Client does not supply run_id

- **WHEN** a client posts a backtest request with no `run_id` field
- **THEN** Research Service generates a `run_id`, persists the run under
  it, and returns it in the response.

#### Scenario: Client attempts to supply run_id

- **WHEN** a client posts a backtest request that includes a `run_id`
  field
- **THEN** the request is rejected before orchestration begins.

### Requirement: Each accepted request creates a new immutable run

Every backtest request that Research Service accepts SHALL create a new
immutable run with a newly generated `run_id`, regardless of whether an
identical strategy instance and evaluation parameters were previously
submitted. Request-level idempotency or deduplication SHALL NOT be part
of this contract.

#### Scenario: Two identical requests produce two runs

- **WHEN** a client submits the same canonical strategy-instance identity
  subset and the same evaluation parameters twice, as two separate
  requests
- **THEN** Research Service creates two separate runs with two distinct
  `run_id` values.
